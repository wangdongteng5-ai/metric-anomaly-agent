# 评估报告：指标异动诊断 Agent（M7，2026-10-08）

## 0. 结论

- **正式成绩（v3，测试集只跑一次）**：动作类型准确率 **17/30 = 57%**，对照周误报 **7/10**；主因 Top-1 63%（规则基线 53%）。
- **执行层可靠，判断层在"没事的周"上不可靠**：方案卡名单一致率 1.000、规则违规 0 条、数字溯源 180/180；诊断层的 3 项未达标（动作准确率、对照周误报、稳定性）都源于同一个问题——对照周里的自然波动与小幅真异常在数据上分不开。
- **开发集 73% → 测试集 57%**：约 −12pp 是对开发集的过拟合（比率效应），约 −4pp 是测试集对照周占比更高（结构效应）。
- **大模型的贡献在测试集上没有复现**：异常题上 v3 = 规则基线 = 14/20，代码执行同样复核标准 15/20；v3 相对基线的领先只来自对照周（误报 7/10 vs 9/10）。
- **v4（修 2 个确定性缺陷）**：开发集回归无变化；测试集按预注册口径 +2 题（19/30 = 63%，事后成绩）。实际跑出 21/30，多出的 2 题是随机波动——单次运行约 ±2 题（±7pp）。

## 3. 动作质量与可信度

| 层 | 指标 | 结果 | 验收线 |
|---|---|---|---|
| ④ | 人群包一致率（代码名单 vs pandas 按策略手册独立重算，Jaccard） | **1.000**（16 个名单） | ≥ 0.9 ✅ |
| ④ | 规则合规（疲劳户 / 频控满 / 每户成本） | **0 条** | 0 条 ✅ |
| ⑤ | 数字溯源率 | **180/180 = 100%**（诊断证据 103 + 方案说明 77） | ≥ 99% ✅ |
| ⑤ | 稳定性（10 题 × 3 次，主因一致） | **8/10 = 80%** | ≥ 90% ❌ |

- **检查有效性**：去掉名单的疲劳 / 频控排除后，S21 名单 110 → 130 户，Jaccard 降到 0.846，能被抓出（变异测试）。
- **稳定性**：异常题 6/6 一致；对照周 2/4（C14、C16 三次指向三个不同分组）。不稳定全部发生在没有真主因的周。
- 21 张方案卡中 7 张来自对照周误报：方案卡本身合规，但诊断错了 → 诊断与方案质量分开评估。
- **数字溯源的局限（M8 回放时发现）**：溯源只检查"数字是否来自材料"，不检查"数字用得对不对"。S25 方案卡写道"35-54 岁·频次体量占比**仅为** 5.389，表明该群体频次较低"：5.389 可以溯源，但它的含义是该组 GMV 变化是整体变化的 5.4 倍（整体变化小，被其他分组抵消）。"仅为""频次较低"都是误读。同一段引用的手册注意事项"先看同期是否有活动刚结束，若有优先考虑补券"恰好指向真答案（活动 27 于 3-26 结束），但系统里没有任何环节执行这项检查。

## 4. badcase 归因（v3 错 13 题）

先判断"谁错了"，再判断"哪一层错了"。

| 归因 | 题 | 证据 | 代码版 |
|---|---|---|---|
| 出题 + 系统 | S31 | 独立日所在周（出题遗漏），周五周六自然 −19% / −14%，叠加缺货后 −34% / −30%，触发"连续 2 天 −30%" | 也错 |
| 工具层：检查范围 | S34 | 提问范围 MEAT-PCKGD 占 GMV 5%，按天噪声大（周一自然 −32%），被判数据问题 | 也错 |

| 模型复核 | S25 | 活动触达·频次分数最负（−2.17 / −2.57），模型选 35-54 岁（活动维度体量显示"不适用"） | 对 |

| 控制层：校验后处理 | S26 | 主因选对，动作写成"召回"，退回后未改，校验不通过的答案照样输出 | 对 |

## 5. 迭代：v4 = v3_h3

| 修复 | 层 | 改动 |
|---|---|---|
| ① 数据质量按天检查改看全平台 | 工具 | tools.py `check_data` 去掉提问范围条件（数据问题通常是全平台的） |
| ② 动作由代码按映射表决定 | 控制 | audit.py `remap`：主因选定后结论类型 / 动作按映射改写，记录"模型原写" |

不调阈值、不改 prompt。

**验证顺序**：本地确认开发集代码判定与候选数不变 → 开发集回归 16/22、误报 3/5，错题集合与 v3 完全相同 → 预注册预期（写入学习进度.md，22:05）→ 冻结 v4（frozen_v3_h3.json）→ 测试集补跑。

| 题 | v3 | v4 | 预期 | 原因 |
|---|---|---|---|---|
| S34 | ❌ | ✅ | 变对 | 修复 ① |
| S26 | ❌ | ✅ | 变对 | 修复 ②（trace：模型仍写"召回"，代码改为"补券"） |
| S31 | ❌ | ❌ | 仍错 | 符合预期 |
| S30、C18 | ❌ | ✅ | 未预期 | 模型随机性 |

| | 动作对 | 对照周误报 |
|---|---|---|
| v3 正式成绩 | 17/30 = 57% | 7/10 |
| v4 事后成绩（预注册口径，只计修复） | 19/30 = 63% | 7/10 |
| v4 实际跑出 | 21/30 = 70% | 6/10 |

- remap 在 C17 也触发（模型写错映射），说明"模型写错动作"会反复出现，交给代码合理。
- **测试集污染**：v4 的修复由测试集错题发现，缺少新的留出集验证泛化；v4 成绩不作泛化证据。

## 6. 大模型贡献了什么

| 证据 | 开发集 | 测试集 |
|---|---|---|
| v3 vs 代码版复核（动作对） | 16 vs 12（模型多对 4 题） | 17 vs 18（模型少 1 题） |
| v3 vs 规则基线（异常题） | 14 vs 11 | 14 vs 14 |

结论：在开发集上看到的"模型复核优于代码规则"**在测试集上没有复现**。模型的稳定价值在于：① 写方案说明（理由、风险、备选手段，数字 100% 可溯源）；② 少数题能结合体量做判断（测试集 S35、开发集 S02）；但也会犯代码不会犯的错（S25、S26、S30）。架构演进的主线是**把能确定的判断不断从模型手里收回给代码**：v2 自主 Agent 5/22 → v3 代码召回 + 模型复核 → v4 动作映射交给代码。

## 7. 局限与下一步

**局限**（补充规格说明书第 14 节）
- 测试集 30 题，单次运行约 ±2 题（±7pp）波动；57% 与 63% 的差距与噪声同量级
- 对照周误报的根源是样本规模（每组一两百户），真实平台规模下组内噪声会小很多
- v4 无新留出集验证
- S31 出题遗漏了独立日
- **分组含未来信息（M8 发现）**：门店头部 / 腰部 / 长尾和用户主力门店按全年 GMV 计算，分析某周时用到了之后的数据（截至 06-26 与全年相比，主力门店分组不同的家庭 211 户 = 8.5%）。改为"按诊断周滚动分组"（只用诊断周之前的数据）后，51 周中 26 周的召回候选不同（几乎全在主力门店维度），05-15 由"正常波动"变为有候选。测试集只能跑一次，且埋异常时按全年分组选人，故**离线评估保留全年分组**；上线诊断（live.py）使用滚动分组
- **注入视图不确定（M8 发现）**："删高价商品"按单价排序时单价相同的商品先后随机（inject.py 第 13 行 ROW_NUMBER 无平局规则），fact_S06 每次查询 GMV 在 83,575～83,590 之间浮动（约 0.02%），未改变任何判定；修法是 ORDER BY 加 product_id，但会改变已冻结的测试集视图，故不修

**下一步**（按证据强弱）
1. **自一致性**：同题跑 3 次，主因不一致判正常波动。稳定性抽样里 C14、C16 可由此消掉误报，异常题主因 6/6 一致不受影响；代价是调用量 × 3。需在开发集验证
2. **复核标准 ④ 引入体量**：S24 / 开发集 S06 同类错误；需权衡对其他题的影响
3. 活动维度补算体量（S25）
4. **"活动刚结束"改由代码检查**：频次或户数下跌时，代码查 campaigns 表中是否有活动在上周结束；命中则给候选打上"活动到期"标记，或直接映射为补券（对应 S25）。该问题由测试集错题发现，修复后需先在开发集验证，再用新的留出集评估。
